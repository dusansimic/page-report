shadcn/ui Mira Migration Plan

page-report dashboard refactor: Custom → Mira UI components

Executive Summary

Replace 8 custom Tailwind primitives (Button, Card, Input, Select, Badge, Table, EmptyState, Skeleton) with shadcn/ui Mira components. Preserve existing color variables; align Mira's compact design (reduced border radius, dense spacing) with dashboard UX. Single-phase migration: 1–2 days development, zero breaking changes to users.

Mira's HSL Defaults (Reference)

Mira provides HSL-based tokens. We will override key shadcn defaults:

/* Mira defaults (from @shadcn-ui/mira template) */ --background: 0 0% 100%; --foreground: 0 0% 3.6%; --primary: 0 0% 9%; --secondary: 0 0% 96.1%; --muted: 0 0% 89.1%; --accent: 0 71.4% 68.6%; /* Mira's teal */ --destructive: 0 84.2% 60.2%; --border: 0 0% 89.1%; --ring: 0 0% 9%;

Adaptation Plan

Decision: Create a custom Tailwind config that maps current CSS variables to shadcn/ui's expected token names. Override Mira's light defaults with dark equivalents.

Rationale:
  • Preserve visual continuity (users see no color change)
  • shadcn/ui Button, Badge, etc. expect --primary, --destructive, etc. to exist
  • Mira's Tailwind config provides a safe template to extend

Migration Phases

Phase 1: Setup (30 min)

Goal: Create Tailwind config extension, add shadcn CLI, install base components.

  • 1.1 Download Mira theme from @shadcn-ui/mira (or GitHub template)
  • 1.2 Extend tailwind.config.ts: override Mira's light colors with current dark variables
  • 1.3 Run npx shadcn-ui@latest init with Mira preset
  • 1.4 Install components: button, card, input, select, badge, table, skeleton
  • 1.5 Test: components render, colors match expectations

Phase 2: Component Migration (4–6 hours)

Goal: Replace custom components with shadcn equivalents in src/components/ui.tsx.

  • 2.1 Migrate Button (primary, secondary, ghost, danger variants)
    • Mira Button supports variant + size
    • No changes needed to call sites
  • 2.2 Migrate LinkButton
    • Breaking: Change from <LinkButton href="…" /> to <Button asChild><a href="…">…</a></Button>
    • Audit call sites: src/routes (likely 2–3 uses)
  • 2.3 Migrate Card (no API change)
  • 2.4 Migrate Input (no API change)
  • 2.5 Migrate Select — DECISION POINT
    Option A (Recommended): Use Radix shadcn/ui Select
    • Pros: Fully accessible (ARIA), keyboard nav, mobile friendly, matches Mira design
    • Cons: API is headless (Radix), requires wrapper components
    • Impact: All <Select><option> call sites need rewrite
    • Effort: ~30 min (2 selects in app)

    Option B (Lighter): Keep native <select>, style with Tailwind
    • Pros: No API change, zero effort, no Radix deps
    • Cons: Native <select> styling is limited; won't match Mira design as closely

    Recommendation: Use Option A (Radix Select). Mira design scales better with proper headless controls; this is a small app.
  • 2.6 Migrate Badge (no API change)
  • 2.7 Migrate Table, Th, Td — shadcn Table is composable; structure stays same
  • 2.8 Migrate Skeleton (no API change)
  • 2.9 Keep EmptyState as custom wrapper (not in shadcn); update to use shadcn Card internally

Phase 3: Call-Site Updates (1–2 hours)

Goal: Update imports and broken APIs in src/routes, src/components.

  • 3.1 Update all imports: from "@/components/ui" → stay same (re-export shadcn from ui.tsx)
  • 3.2 Fix LinkButton call sites (estimated 2–3 places)
  • 3.3 Fix Select call sites (estimated 2 places: Tokens screen, filters)
  • 3.4 Run TypeScript check: pnpm typecheck
  • 3.5 Run lint: pnpm lint

Phase 4: QA & Polish (1 hour)

Goal: Verify visual consistency, test accessibility, confirm Mira design intent.

  • 4.1 Visual regression: take screenshots of all 3 screens, compare to baseline
  • 4.2 Test Button variants (primary, secondary, ghost, danger, disabled)
  • 4.3 Test Badge tones (muted, good, warn, bad)
  • 4.4 Test Select keyboard nav (arrow keys, Enter, Escape)
  • 4.5 Test Table sorting/pagination (if applicable)
  • 4.6 Verify dark theme in browser dev tools
  • 4.7 Run production build: pnpm build and test dist

Risk & Mitigation

Risk: Select API Breakage

Issue: Native <select> → Radix Select is a large API change (headless wrapper).

Mitigation:

  • Only 2–3 select call sites in the app (small blast radius)
  • Radix Select is well-documented; shadcn examples are abundant
  • Consider keeping native select as fallback if time-constrained

Risk: Color Drift

Issue: Mira's defaults might override custom vars; CSS specificity issues.

Mitigation:

  • Map all shadcn token names to existing vars (above)
  • Test colors in browser DevTools after Phase 1
  • If colors drift, adjust tailwind.config.ts theme.extend

Risk: Dependencies Conflict

Issue: Radix UI might conflict with existing React versions or other deps.

Mitigation:

  • React 19.2.8 is cutting edge but stable; Radix supports it
  • shadcn/ui is tested with React 18+
  • Install and run pnpm install first; resolve any peer warnings

Build & Deployment Notes

  • Bundle impact: shadcn/ui + Radix adds ~30–50 KB gzipped (typical for Button + Select + Table). Current app is small, so acceptable.
  • Tree-shaking: Only imported components are bundled. Unused shadcn components do not bloat the build.
  • Generated files: shadcn components are generated into src/components/ui/; commit them to git.
  • Vite: No vite config changes needed. Tailwind v4 plugin already handles CSS.
  • SSR/Edge: Not applicable (SPA only). shadcn/ui is fully client-side.
